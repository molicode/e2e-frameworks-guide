Verbos HTTP

Una API REST se maneja con verbos HTTP: cada uno declara una intención (leer, crear, reemplazar, borrar…). Testear una API es, en gran parte, disparar el verbo correcto y verificar el código de estado y el cuerpo de la respuesta. Acá los ves todos, en el idiom de este framework.

Teoría

Dos conceptos que toda entrevista pregunta: el código de estado (2xx ok, 4xx error del cliente, 5xx error del servidor) y la idempotencia — si repetir la misma llamada deja el sistema igual. GET, PUT y DELETE son idempotentes; POST no (cada llamada crea algo nuevo). PATCH suele serlo, pero depende de cómo lo implementes.

Los verbos de un vistazo

VerboQué haceIdempotenteStatus típico
GETLeer un recurso (no lo modifica)Sí200
POSTCrear un recurso nuevoNo201
PUTReemplazar el recurso completoSí200 / 204
PATCHActualizar parte del recursoSuele serlo200
DELETEEliminar el recursoSí204
HEADComo GET pero solo headers (sin cuerpo)Sí200
OPTIONSQué métodos permite el recurso (CORS)Sí200 / 204

En proyectos Python (incluido Selenium) la librería requests es el estándar para la capa de API. Tiene un método por verbo: get, post, put, patch, delete, head, options.

Cada llamada devuelve una respuesta con .status_code, .json() y .headers. Para OPTIONS, los métodos permitidos vienen en el header Allow.

Python 
# Todos los verbos HTTP con requests. El status code te dice qué pasó.
import requests

base = "https://api.example.com"
auth = {"Authorization": f"Bearer {token}"}

# GET — leer un recurso (seguro, idempotente).
assert requests.get(f"{base}/orders/42", headers=auth).status_code == 200

# POST — crear un recurso nuevo (NO idempotente: un id nuevo cada vez).
created = requests.post(f"{base}/orders", json={"items": ["book"]}, headers=auth)
assert created.status_code == 201
order_id = created.json()["id"]

# PUT — reemplazar el recurso ENTERO (idempotente).
put = requests.put(f"{base}/orders/{order_id}",
                   json={"items": ["pen"], "status": "NEW"}, headers=auth)
assert put.status_code == 200

# PATCH — actualizar PARTE del recurso (idempotente en la práctica).
assert requests.patch(f"{base}/orders/{order_id}",
                      json={"status": "PAID"}, headers=auth).status_code == 200

# DELETE — eliminarlo (idempotente: borrar dos veces igual queda "gone").
assert requests.delete(f"{base}/orders/{order_id}", headers=auth).status_code == 204

# HEAD — como GET pero solo headers, sin body (barato "¿existe?").
assert requests.head(f"{base}/orders/42", headers=auth).status_code == 200

# OPTIONS — qué métodos están permitidos (CORS preflight / descubrimiento).
opt = requests.options(f"{base}/orders", headers=auth)
assert "POST" in opt.headers.get("Allow", "")# Every HTTP verb with requests. The status code tells you what happened.
import requests

base = "https://api.example.com"
auth = {"Authorization": f"Bearer {token}"}

# GET — read a resource (safe, idempotent).
assert requests.get(f"{base}/orders/42", headers=auth).status_code == 200

# POST — create a new resource (NOT idempotent: a new id each time).
created = requests.post(f"{base}/orders", json={"items": ["book"]}, headers=auth)
assert created.status_code == 201
order_id = created.json()["id"]

# PUT — replace the WHOLE resource (idempotent).
put = requests.put(f"{base}/orders/{order_id}",
                   json={"items": ["pen"], "status": "NEW"}, headers=auth)
assert put.status_code == 200

# PATCH — update PART of the resource (idempotent in practice).
assert requests.patch(f"{base}/orders/{order_id}",
                      json={"status": "PAID"}, headers=auth).status_code == 200

# DELETE — remove it (idempotent: deleting twice still ends "gone").
assert requests.delete(f"{base}/orders/{order_id}", headers=auth).status_code == 204

# HEAD — like GET but headers only, no body (cheap "does it exist?").
assert requests.head(f"{base}/orders/42", headers=auth).status_code == 200

# OPTIONS — which methods are allowed (CORS preflight / discovery).
opt = requests.options(f"{base}/orders", headers=auth)
assert "POST" in opt.headers.get("Allow", "")
Regla práctica: verificá primero el status y después el cuerpo. Y testeá los caminos infelices: sin token → 401, recurso de otro usuario → 403, id inexistente → 404. Un 200 que debería ser un 404 es un bug.
