Conceptos clave

El vocabulario que más cae en una entrevista de QA, ordenado por tema. Definiciones cortas y al hueso para repasar antes de la charla.

Proceso y estrategia

SDLC / STLC SDLC es el ciclo de vida del software; STLC es el del testing dentro de él (planificación, diseño, ejecución, cierre).
Shift-left testing Mover el testing lo más temprano posible (incluso antes de codear): es más barato arreglar un bug en diseño que en producción.
TDD (Test-Driven Development) Escribís el test antes que el código: rojo → verde → refactor. Guía el diseño y deja una red de seguridad.
BDD (Gherkin / Cucumber) Describís el comportamiento en lenguaje Given/When/Then (Gherkin); herramientas como Cucumber lo conectan al código.
ATDD Acceptance Test-Driven: el equipo define juntos los criterios de aceptación como tests antes de desarrollar.
Regression testing Re-correr pruebas existentes para confirmar que un cambio no rompió funcionalidad que ya andaba.
Smoke vs Sanity Smoke: ¿lo más crítico funciona? Sanity: chequeo rápido y acotado tras un fix puntual.
Exploratory testing Probar sin guion, diseñando y ejecutando a la vez, para descubrir lo que los casos escritos no previeron.
Acceptance / UAT User Acceptance Testing: el usuario/negocio valida que el sistema cumple sus criterios antes de salir a producción.
Risk-based testing Priorizás qué probar según probabilidad e impacto del fallo: más esfuerzo donde más duele.
Data-driven testing Un mismo test corre con muchos sets de datos (tabla/CSV/JSON), separando la lógica de los datos.

Diseño de casos

Equivalence Partitioning Agrupás entradas que el sistema trata igual y probás un representante de cada grupo (válido e inválido).
Boundary Value Analysis Probás los bordes de cada rango (mín, mín±1, máx, máx±1): ahí se esconde la mayoría de los bugs.
Decision Table Tabla que mapea combinaciones de condiciones a la acción/resultado esperado; ideal para lógica con muchos ifs.
State Transition Modelás los estados y las transiciones válidas e inválidas (nueva → pagada → reembolsada) y probás los caminos.
Pairwise / Combinatorial Técnica combinatoria que cubre todos los pares de valores con muchos menos casos que el total de combinaciones.
Traceability Matrix Matriz que vincula requisitos ↔ casos de prueba para ver qué quedó sin cubrir.

Defectos

Severity vs Priority Severidad = impacto técnico del bug; prioridad = qué tan urgente es arreglarlo. Pueden no coincidir.
Defect lifecycle El recorrido de un defecto: nuevo → asignado → en progreso → corregido → re-test → cerrado (o reabierto).
Root Cause Analysis (RCA) Análisis de causa raíz: ir más allá del síntoma para encontrar el origen real y evitar que vuelva a pasar.
Triage Reunión/decisión para clasificar y priorizar bugs: qué se arregla ahora, qué después y qué no.
Reproducible steps Pasos claros y mínimos para reproducir el bug; sin ellos, el reporte es casi inútil.

Automatización

Assertion La afirmación que decide si el test pasa o falla: compara lo real contra lo esperado.
Selector / Locator La estrategia para encontrar un elemento (rol, etiqueta, texto, data-testid, CSS, XPath).
Page Object Model (POM) Patrón que encapsula los selectores y acciones de una página en una clase reutilizable.
Fixtures Mecanismo para preparar y proveer estado/dependencias a un test (datos, sesión, página).
Hooks (setup / teardown) Ganchos que corren antes/después (beforeEach, afterAll) para setup y limpieza.
Test doubles (mock / stub / spy / fake) Objetos falsos que reemplazan dependencias: mock, stub, spy, fake y dummy.
Implicit / Explicit / Fluent wait Implícita (global), explícita (espera una condición puntual) y fluent (con polling y timeout configurables).
Auto-wait / retry El framework reintenta la acción/assertion hasta que se cumple o expira, en vez de esperar a ciegas.
Flaky test Test que a veces pasa y a veces falla sin cambiar el código; suele ser por esperas o datos compartidos.
Headless Correr el navegador sin interfaz gráfica: más rápido, ideal para CI.
Parallelization Ejecutar muchos tests a la vez para acortar el tiempo total de la suite.
Cross-browser Verificar que la app funciona en distintos navegadores/motores (Chromium, Firefox, WebKit).
Code coverage Cuánto del código ejecutan tus tests (por sentencia, rama, función). Útil, pero no garantiza calidad.
CI/CD & quality gate Correr la suite automáticamente en cada cambio; un quality gate bloquea el merge si algo está rojo.
Test isolation / idempotency Cada test crea y limpia sus datos y no depende de otros; corre igual solo o en cualquier orden.
Test data management Gestión de datos de prueba: crearlos, aislarlos y limpiarlos para tener tests deterministas.
Visual regression Comparar capturas contra una referencia para detectar cambios visuales no deseados.
Accessibility (a11y) testing Probar accesibilidad: roles ARIA, navegación por teclado, contraste y lectores de pantalla.
API testing Probar la API directamente (sin UI): status codes, contratos y payloads; más rápido y estable.

AI en QA

Prompt engineering Diseñar la instrucción (rol, contexto, restricciones, formato) para obtener mejor salida del modelo.
Hallucination Cuando la AI inventa algo plausible pero falso (un selector o método que no existe). Siempre validá.
Self-healing locators Locators que se reajustan solos cuando el DOM cambia, reduciendo el mantenimiento de selectores frágiles.
LLM test generation Usar un LLM para generar casos o código de test a partir de una historia, el HTML o los criterios.
Human-in-the-loop Human-in-the-loop: la AI propone, una persona revisa y decide. La responsabilidad final es humana.
MCP (Model Context Protocol) Model Context Protocol: estándar abierto que conecta al modelo con herramientas y datos externos.
Skill Capacidad reutilizable que empaqueta instrucciones/convenciones para repetir un flujo de forma consistente.
Agent / sub-agent Sistema de AI que planifica y ejecuta varios pasos con herramientas; los sub-agentes dividen el trabajo.
RAG (Retrieval-Augmented Generation) Retrieval-Augmented Generation: el modelo consulta tu documentación/datos para responder con contexto real.
Context window / tokens La ventana de tokens que el modelo puede ver a la vez; limita cuánto contexto entra de una.

Seguridad

Authentication vs Authorization Authentication = quién sos (login); Authorization = qué podés hacer (permisos). Se prueban distinto.
IDOR Insecure Direct Object Reference: acceder a un recurso ajeno cambiando un id/parámetro. Debe dar 403, no 200.
XSS (Cross-Site Scripting) Cross-Site Scripting: inyectar scripts que el navegador ejecuta. La defensa: escapar/sanitizar la salida.
SQL Injection Inyección de SQL vía entradas sin sanitizar. La defensa: consultas parametrizadas, nunca concatenar SQL.
CSRF Cross-Site Request Forgery: forzar acciones en nombre de un usuario logueado. La defensa: tokens anti-CSRF.
Rate limiting Limitar la cantidad de requests por tiempo para frenar fuerza bruta y abuso (ej. login).
Least privilege Principio de mínimo privilegio: cada usuario/servicio tiene solo los permisos que necesita, nada más.
Sensitive data exposure Exposición de datos sensibles: tokens, contraseñas o tarjetas filtrados en respuestas, logs o URLs.
Tip de entrevista: no alcanza con definir — tené un ejemplo de cada término. “Un test flaky es… por ejemplo, cuando usás un sleep fijo y la red tarda más de la cuenta.”
