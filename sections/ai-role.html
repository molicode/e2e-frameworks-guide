El rol de la AI

La AI no vino a reemplazar al QA, sino a amplificarlo. Es como tener un par junior infinito: rápido, incansable y que a veces se equivoca. Tu trabajo pasa de escribir todo a dirigir y validar.

Teoría

La AI puede asistir en cada etapa del ciclo de testing, pero siempre con un humano en el bucle. El patrón es el mismo: la AI propone, vos disponés. Veamos dónde aporta valor.

Dónde ayuda la AI

🧩

Generar casos

A partir de una historia de usuario, propone escenarios: happy path, edge cases y errores que se te pasaron.

✍️

Escribir código

Traduce un caso a código de test en el framework que elijas, con la sintaxis correcta.

🎯

Selectores robustos

Sugiere selectores estables (por rol, etiqueta o data-testid) en lugar de xpaths frágiles.

🔁

Detectar flaky

Analiza un test inestable y señala esperas fijas, datos compartidos o condiciones de carrera.

🩺

Explicar fallos

Lee el error, el stack trace o la traza y explica en lenguaje claro la causa más probable.

Skills, MCP y Agentes

La AI rinde mucho más cuando le das herramientas, contexto y autonomía. Tres piezas modernas que potencian el testing automation:

🧩

Skills

Instrucciones reutilizables que encapsulan las convenciones de tu equipo (POM, política de selectores) para generar tests consistentes.

🔌

MCP

El Model Context Protocol conecta a la AI con herramientas reales: un navegador, tu repo, el issue tracker, los logs de CI.

🤖

Agentes

Agentes que planifican y ejecutan varios pasos: generan el test, lo corren, leen el fallo y lo arreglan en un bucle.

Con MCP la AI deja de adivinar: puede abrir la app, leer el árbol de accesibilidad y proponer selectores que existen de verdad.

JSON 
// Dale a la IA herramientas reales vía servidores MCP (puede manejar un navegador, leer
// el DOM/árbol de accesibilidad en vivo, abrir PRs, consultar tu issue tracker).
{
  "mcpServers": {
    "playwright": { "command": "npx", "args": ["@playwright/mcp@latest"] },

Una Skill es como un comando con el know-how de tu equipo adentro: en vez de re-explicar tus reglas en cada prompt, los tests salen siempre con el mismo estándar.

Markdown 
# Skill: generate-e2e  (las convenciones de tu equipo, reutilizadas cada vez)

Cuando te pidan escribir un test end-to-end:
- Usá Playwright + los Page Objects en src/pages/.
- Selectores: getByRole / getByTestId solamente — nunca CSS ni XPath.
- Una intención por test, aserciones web-first, cero esperas fijas.
- Mockeá la red con page.route(); nunca pegues al backend real.

# Un skill empaqueta este know-how para que cada test generado siga los
# mismos estándares — sin necesidad de re-explicarlos en cada prompt.# Skill: generate-e2e  (your team's conventions, reused every time)

When asked to write an end-to-end test:
- Use Playwright + the Page Objects in src/pages/.
- Selectors: getByRole / getByTestId only — never CSS or XPath.
- One intent per test, web-first assertions, zero fixed sleeps.
- Mock the network with page.route(); never hit the real backend.

# A skill packages this know-how so every generated test follows the
# same standards — no need to re-explain them in each prompt.

Un agente cierra el lazo. Y con varios agentes (uno escribe, otro intenta refutar) subís la confianza antes de commitear.

Text 
Bucle de agente — autónomo "escribir → correr → leer la falla → corregir":

  1. Leé la historia de usuario + criterios de aceptación.
  2. Generá el test de Playwright (usando el Skill del equipo de arriba).
  3. Corrélo vía el servidor MCP de Playwright.
  4. Si falla: leé el error + traza, ubicá la causa, parcheá el test.
  5. Repetí hasta que esté en verde, luego abrí un PR.

Variante multi-agente (mayor confianza):
  - Agente Escritor  -> redacta el test.
  - Agente Revisor -> intenta REFUTARLO: "¿puede pasar incluso si la app está
    rota?" Solo los tests que sobreviven la revisión se commitean.Agent loop — autonomous "write → run → read failure → fix":

  1. Read the user story + acceptance criteria.
  2. Generate the Playwright test (using the team Skill above).
  3. Run it via the Playwright MCP server.
  4. If it fails: read the error + trace, locate the cause, patch the test.
  5. Repeat until green, then open a PR.

Multi-agent variant (higher confidence):
  - Writer agent  -> drafts the test.
  - Reviewer agent -> tries to REFUTE it: "can this pass even if the app is
    broken?" Only tests that survive the review get committed.

Manual vs AI

Manual Flujo manual

Vos redactás el caso de prueba a mano, pensando cada escenario y cada dato esperado. Preciso, pero lento de escalar.

Text 
Caso de prueba (escrito a mano):

  Título:   La orden 42 está pagada y contiene un libro
  Pasos:    1. Abrir /orders/42
            2. Leer el total, el estado y la lista de ítems
  Esperado: total = 250, status = PAID, items include "book"Test case (written by hand):

  Title:    Order 42 is paid and contains a book
  Steps:    1. Open /orders/42
            2. Read the total, status and item list
  Expected: total = 250, status = PAID, items include "book"
Con AI Flujo asistido por AI

Le das contexto y un objetivo, y la AI genera el borrador de casos en segundos. Después vos lo revisás, recortás y completás.

Prompt 
Sos un ingeniero QA senior. Generá CASOS de prueba (no código) para la
página de resumen de orden de abajo. Cubrí happy path, casos límite y estados de error.

Página: resumen de orden en /orders/:id
Campos mostrados: total (número), status (NEW | PAID | REFUNDED), lista de ítems.

Devolvé una tabla: id | título | precondiciones | pasos | resultado esperado.
Marcá qué casos son buenos candidatos para automatización y por qué.You are a senior QA engineer. Generate test CASES (not code) for the
order-summary page below. Cover happy path, edge cases and error states.

Page: order summary at /orders/:id
Fields shown: total (number), status (NEW | PAID | REFUNDED), item list.

Return a table: id | title | preconditions | steps | expected result.
Mark which cases are good candidates for automation and why.
Regla de oro: la AI es un acelerador, no un oráculo. Puede inventar selectores que no existen o assertions que no reflejan los criterios de aceptación. Nunca mergees código de test que no entendiste y no corriste.
