Ruta de aprendizaje

  1. Comandos y la cadena async — cy.get() no devuelve un valor directo: encadenás. Esto es lo que más cuesta al principio.
  2. Assertions y selectores — Las .should() implícitas y explícitas; la convención data-cy.
  3. Network con cy.intercept() — Mockeá APIs, esperá requests con alias y testeá estados de error.
  4. Custom commands y fixtures — Encapsulá el login y los datos en fixtures JSON para tests limpios.
  5. Component testing + CI — Probá componentes aislados y armá la corrida en el pipeline.

Comandos y la cadena async

El concepto que más cuesta: los comandos cy.* no son promesas y no devuelven un valor directo — se encolan y se encadenan. Si necesitás el valor de un elemento usás .then(), pero conviene evitarlo. Con .as() creás un alias y lo reusás con @nombre.

TypeScript 
// Los comandos cy.* NO son promesas — encolan trabajo. Encadenás, no usás await.
cy.get("#username").type("demo");          // encolado
cy.get("button[type=submit]").click();     // corre después de que resuelve el type

// ¿Necesitás el *valor*? Usá .then() — pero recurrí a él con moderación.
cy.get(".order-total").then(($el: JQuery<HTMLElement>) => {
  expect($el.text()).to.eq("250");
});

// Aliasá una consulta con .as() y reutilizala más tarde con @:
cy.get(".order-items li").as("items");
cy.get("@items").should("have.length", 3);// cy.* commands are NOT promises — they enqueue work. You chain, you don't await.
cy.get("#username").type("demo");          // queued
cy.get("button[type=submit]").click();     // runs after the type resolves

// Need the *value*? Use .then() — but reach for it sparingly.
cy.get(".order-total").then(($el: JQuery<HTMLElement>) => {
  expect($el.text()).to.eq("250");
});

// Alias a query with .as() and reuse it later with @:
cy.get(".order-items li").as("items");
cy.get("@items").should("have.length", 3);

Assertions y selectores

Las assertions de Cypress son implícitas: .should() reintenta el comando anterior hasta que se cumple. Encadenás más condiciones con .and(), o usás expect() dentro de un callback para casos explícitos. Para selectores estables, la comunidad usa la convención data-cy.

TypeScript 
// Las aserciones implícitas reintentan el comando anterior hasta que pasan:
cy.get(".order-status").should("have.text", "PAID");
cy.get(".order-items li").should("have.length", 3).and("contain", "book");

// Aserciones explícitas con expect() dentro de un callback de .should():
cy.get(".order-total").should(($el: JQuery<HTMLElement>) => {
  expect($el.text().trim()).to.eq("250");
});

// Preferí un atributo de test dedicado en vez de css frágil:
//   <button data-cy="pay">Pay</button>
cy.get("[data-cy=pay]").click();// Implicit assertions retry the previous command until they pass:
cy.get(".order-status").should("have.text", "PAID");
cy.get(".order-items li").should("have.length", 3).and("contain", "book");

// Explicit assertions with expect() inside a .should() callback:
cy.get(".order-total").should(($el: JQuery<HTMLElement>) => {
  expect($el.text().trim()).to.eq("250");
});

// Prefer a dedicated test attribute over brittle css:
//   <button data-cy="pay">Pay</button>
cy.get("[data-cy=pay]").click();

Network con cy.intercept()

Con cy.intercept() interceptás y mockeás las llamadas de red: devolvés datos fijos para tests rápidos y deterministas. Le ponés un alias con .as() y esperás la request con cy.wait('@alias') — nunca un sleep. Cambiando el statusCode probás estados de error (500, 404).

TypeScript 
// Mockeá la API: datos deterministas, sin backend real, tests instantáneos.
cy.intercept("GET", "/api/orders/42", {
  statusCode: 200,
  body: { total: 250, status: "PAID", items: ["book"] },
}).as("getOrder");

cy.visit("/orders/42");
cy.wait("@getOrder");                       // esperá la request, no un sleep
cy.get(".order-total").should("have.text", "250");

// Probá un estado de error mockeando un 500:
cy.intercept("GET", "/api/orders/*", { statusCode: 500 }).as("boom");// Stub the API: deterministic data, no real backend, instant tests.
cy.intercept("GET", "/api/orders/42", {
  statusCode: 200,
  body: { total: 250, status: "PAID", items: ["book"] },
}).as("getOrder");

cy.visit("/orders/42");
cy.wait("@getOrder");                       // wait for the request, not a sleep
cy.get(".order-total").should("have.text", "250");

// Test an error state by stubbing a 500:
cy.intercept("GET", "/api/orders/*", { statusCode: 500 }).as("boom");

Custom commands y fixtures

Repetís un flujo (como el login) en muchos tests: encapsulalo una vez con Cypress.Commands.add() y reusalo en todos. cy.session() cachea la sesión para no re-loguear. Los datos de prueba viven en fixtures JSON y se cargan con cy.fixture().

TypeScript 
// cypress/support/commands.ts — encapsulá flujos repetitivos una sola vez.
Cypress.Commands.add("login", (user: string, pass: string) => {
  cy.session([user], () => {
    cy.visit("/login");
    cy.get("[data-cy=user]").type(user);
    cy.get("[data-cy=pass]").type(pass);
    cy.get("[data-cy=submit]").click();
  });
});

// Enseñale a TypeScript el nuevo comando (cypress/support/index.d.ts):
declare global {
  namespace Cypress {
    interface Chainable {
      login(user: string, pass: string): void;
    }
  }
}

cy.login("demo", "secret");// cypress/support/commands.ts — encapsulate repetitive flows once.

Component testing + CI

Además de E2E, Cypress hace component testing: montás un componente aislado con cy.mount() y lo probás sin levantar toda la app. En CI corrés cypress run (headless), con --component o --e2e según el tipo.

TypeScript 
// button.cy.tsx — montá un componente en aislamiento (no hace falta la app completa).
import Button from "./Button";

it("calls onClick", () => {
  const onClick = cy.stub().as("onClick");
  cy.mount(<Button onClick={onClick}>Pay</Button>);
  cy.get("button").click();
  cy.get("@onClick").should("have.been.calledOnce");
});

// En CI:  npx cypress run --component   (y --e2e para end-to-end)// button.cy.tsx — mount a component in isolation (no full app needed).

});
