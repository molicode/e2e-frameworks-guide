Prompt engineering

Un buen resultado empieza por un buen prompt. La clave es dar contexto, restricciones y formato de salida. Veamos prompts concretos y cómo iterar y validar lo que la AI produce.

Prompt para generar un test

Incluí siempre cuatro cosas: rol (“sos QA senior”), contexto (URL, selectores), objetivo (qué verificar) y restricciones (sin sleeps, assertions web-first). Cuanto más específico, menos alucina.

Prompt 
Sos un ingeniero QA senior. Escribí un test de Playwright en Python (pytest).

Contexto:
- Página: https://shop.example.com/orders/42  (un resumen de orden)
- Selectores estables: .order-total, .order-status, .order-items li

El test "test_verify_order" debe afirmar:
- .order-total      tiene el texto "250"
- .order-status     tiene el texto "PAID"
- .order-items      contiene un ítem cuyo texto incluye "book"

Requisitos:
- Usá aserciones web-first (expect(...).to_have_text / to_contain_text).
- Sin esperas fijas. Sin lógica condicional (if/else) en el test.
- Un comentario corto sobre cada aserción explicando la intención.You are a senior QA engineer. Write a Playwright test in Python (pytest).

Context:
- Page: https://shop.example.com/orders/42  (an order summary)
- Stable selectors: .order-total, .order-status, .order-items li

Test "test_verify_order" must assert:
- .order-total      has text "250"
- .order-status     has text "PAID"
- .order-items      contains an item whose text includes "book"

Requirements:
- Use web-first assertions (expect(...).to_have_text / to_contain_text).
- No fixed sleeps. No conditional (if/else) logic in the test.
- One short comment above each assertion explaining intent.

Cómo iterar sobre el output

Casi nunca el primer intento es perfecto. Iterá con feedback corto y concreto:

  • “El selector .total no existe; usá .order-total.”
  • “Quitá el cy.wait(2000) y confiá en el auto-retry.”
  • “Agregá un caso para status = REFUNDED.”

Tratá a la AI como a un colega: respuestas cortas, ejemplos del resultado esperado y un cambio por vez.

Cómo validar lo que produjo

No confíes a ciegas. Revisá el código generado como si fuera un pull request de alguien más:

Python 
# Salida de la IA — revisala como lo harías con el pull request de un dev junior.
from playwright.sync_api import Page, expect


def test_verify_order(page: Page):
    page.goto("https://shop.example.com/orders/42")
    expect(page.locator(".order-total")).to_have_text("250")
    expect(page.locator(".order-status")).to_have_text("PAID")
    expect(page.locator(".order-items li")).to_contain_text("book")


# Checklist antes de confiar en ella:
#  - Los selectores realmente existen en la app (no lo asumas).
#  - Las aserciones coinciden con los CRITERIOS DE ACEPTACIÓN, no solo el happy path.
#  - Sin esperas/sleeps ocultos, sin tests que nunca puedan fallar.
#  - Falla cuando debe: rompé temporalmente la app y volvé a correr.# AI output — review it the way you would a junior dev's pull request.
from playwright.sync_api import Page, expect


def test_verify_order(page: Page):
    page.goto("https://shop.example.com/orders/42")
    expect(page.locator(".order-total")).to_have_text("250")
    expect(page.locator(".order-status")).to_have_text("PAID")
    expect(page.locator(".order-items li")).to_contain_text("book")


# Checklist before you trust it:
#  - Selectors actually exist in the app (don't assume).
#  - Assertions match the ACCEPTANCE CRITERIA, not just the happy path.
#  - No hidden waits/sleeps, no test that can never fail.
#  - It fails when it should: temporarily break the app and re-run.

Manual vs AI

Manual Flujo manual

Vos redactás el caso de prueba a mano, pensando cada escenario y cada dato esperado. Preciso, pero lento de escalar.

Text 
Caso de prueba (escrito a mano):

  Título:   La orden 42 está pagada y contiene un libro
  Pasos:    1. Abrir /orders/42
            2. Leer el total, el estado y la lista de ítems
  Esperado: total = 250, status = PAID, items include "book"Test case (written by hand):

  Title:    Order 42 is paid and contains a book
  Steps:    1. Open /orders/42
            2. Read the total, status and item list
  Expected: total = 250, status = PAID, items include "book"
Con AI Flujo asistido por AI

Le das contexto y un objetivo, y la AI genera el borrador de casos en segundos. Después vos lo revisás, recortás y completás.

Prompt 
Sos un ingeniero QA senior. Generá CASOS de prueba (no código) para la
página de resumen de orden de abajo. Cubrí happy path, casos límite y estados de error.

Página: resumen de orden en /orders/:id
Campos mostrados: total (número), status (NEW | PAID | REFUNDED), lista de ítems.

Devolvé una tabla: id | título | precondiciones | pasos | resultado esperado.
Marcá qué casos son buenos candidatos para automatización y por qué.You are a senior QA engineer. Generate test CASES (not code) for the
order-summary page below. Cover happy path, edge cases and error states.

Page: order summary at /orders/:id
Fields shown: total (number), status (NEW | PAID | REFUNDED), item list.

Return a table: id | title | preconditions | steps | expected result.
Mark which cases are good candidates for automation and why.
No confíes a ciegas: la AI puede producir tests que siempre pasan (y por lo tanto no sirven). Verificá que el test FALLE cuando debe: rompé el comportamiento a propósito y confirmá que se pone en rojo.
