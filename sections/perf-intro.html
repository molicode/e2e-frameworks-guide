Performance

Qué es y qué se mide

El testing funcional pregunta “¿hace lo correcto?”; el performance testing pregunta “¿lo hace rápido y estable bajo carga?”. Simulás muchos usuarios en paralelo y medís cómo responde el sistema: velocidad, estabilidad y escalabilidad.

Teoría

No es un solo tipo de prueba. Según cómo apliques la carga, hablás de load (carga esperada), stress (hasta romperlo), spike (picos bruscos) o soak (carga sostenida por horas, para detectar memory leaks). Cada uno responde una pregunta distinta sobre el sistema.

📈

Load

Carga esperada (los usuarios de un día normal): ¿cumple los tiempos objetivo?

🔥

Stress

Subís la carga hasta que algo se rompe, para encontrar el límite y ver cómo falla.

⚡

Spike

Un pico brusco y repentino (una promo, un viral): ¿aguanta y se recupera?

⏳

Soak / endurance

Carga moderada sostenida por horas: detecta fugas de memoria y degradación lenta.

Las métricas que importan

El promedio engaña: si el 95% de los usuarios espera 200ms pero el 5% espera 8s, el promedio se ve bien y la experiencia es mala. Por eso se miran percentiles (p95, p99), no medias.

MétricaQué mide
Throughput (RPS)Requests por segundo que el sistema procesa. Cuánto “mueve”.
Latencia (p95 / p99)Cuánto tarda una request. Mirá los percentiles, no el promedio.
Error ratePorcentaje de requests que fallan al subir la carga. Debe quedar bajo (&lt; 1%).
VUs / concurrenciaUsuarios virtuales simultáneos que estás simulando.
SaturaciónUso de recursos (CPU, memoria, conexiones) al subir la carga. Dónde está el cuello de botella.
Definí el objetivo primero: un test de performance sin un SLO (“el p95 debe ser < 500ms con 200 usuarios”) solo genera números. El número se vuelve útil cuando hay un umbral de pasa/no pasa contra el cual compararlo.
