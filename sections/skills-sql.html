SQL para QA

El testing es validar datos, y muchos viven en una base relacional. Con saber leer (no hace falta ser DBA) ya verificás un montón: que un pago se guardó, que no hay duplicados, que los montos cierran.

Leer datos: SELECT

El 90% del SQL para QA es leer. SELECT elige columnas, FROM la tabla, WHERE filtra filas, ORDER BY ordena y LIMIT acota. Con eso ya inspeccionás lo que tu test dejó en la base.

SQL 
-- Leé datos para verificar lo que creó tu test. Empezá simple.
SELECT id, status, total
FROM orders
WHERE status = 'PAID'          -- filtrá filas
ORDER BY total DESC            -- primero las más grandes
LIMIT 10;                      -- solo las 10 primeras-- Read data to verify what your test created. Start simple.
SELECT id, status, total
FROM orders
WHERE status = 'PAID'          -- filter rows
ORDER BY total DESC            -- biggest first
LIMIT 10;                      -- only the top 10

Cruzar tablas: JOIN y agregaciones

Los datos están repartidos en tablas relacionadas. Un JOIN las cruza por su clave. Sumá COUNT, SUM, GROUP BY y HAVING para encontrar problemas: usuarios duplicados, totales que no cuadran, pedidos huérfanos.

SQL 
-- Uní tablas relacionadas y agregá para detectar problemas de datos.
SELECT u.email, COUNT(o.id) AS orders, SUM(o.total) AS spent
FROM users u
JOIN orders o ON o.user_id = u.id      -- relacioná los pedidos con su usuario
WHERE o.status = 'PAID'
GROUP BY u.email
HAVING COUNT(o.id) > 1;                -- usuarios con más de un pedido-- Join related tables and aggregate to spot data problems.
SELECT u.email, COUNT(o.id) AS orders, SUM(o.total) AS spent
FROM users u
JOIN orders o ON o.user_id = u.id      -- match orders to their user
WHERE o.status = 'PAID'
GROUP BY u.email
HAVING COUNT(o.id) > 1;                -- users with more than one order

Validar la DB desde un test

El truco más potente: después de una acción en la UI, verificá la base directamente. La UI puede mostrar "PAID" por un cache o un bug visual; la fila en la tabla no miente. Una query dentro del test cierra el círculo.

Python 
# Validá el estado de la BASE DE DATOS después de una acción — la UI puede mentir, los datos no.
import sqlite3


def test_payment_persists_in_db():
    conn = sqlite3.connect("shop.db")
    row = conn.execute(
        "SELECT status, total FROM orders WHERE id = ?", (42,)
    ).fetchone()
    conn.close()

    # Lo que la UI mostró como PAID debe estar realmente como PAID en la base de datos.
    assert row == ("PAID", 250)# Validate the DATABASE state after an action — the UI can lie, the data can't.

Cuidá la base de pruebas: consultá datos de test, nunca de producción, y preferí transacciones o datos sembrados (seeds) que puedas limpiar. Un SELECT es inofensivo; un DELETE sin WHERE, no.
