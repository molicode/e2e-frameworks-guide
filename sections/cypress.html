04 Cypress

Cypress

Cypress reinventó la experiencia de escribir tests E2E con un runner visual, recarga en vivo y una API encadenable pensada para la felicidad del desarrollador.

Filosofía

Cypress corre dentro del navegador, en el mismo loop de ejecución que tu app. Esto le da acceso directo al DOM y un auto-retry incorporado: cada comando se reintenta hasta que pasa o expira. Su API es encadenable (cy.get(...).should(...)) y muy legible.

Cuándo usarlo

Elegí Cypress para apps web modernas (especialmente SPAs) donde valorás una DX excelente, el time-travel debugger y una curva de aprendizaje suave. Tené en cuenta sus límites: foco en Chromium/Firefox y un modelo de una sola pestaña/origen (aunque mejoró con los años).

Ruta de aprendizaje

  1. El runner interactivo — Corré cypress open, mirá el time-travel y entendé describe / it.
  2. Comandos y la cadena async — cy.get() no devuelve un valor directo: encadenás. Esto es lo que más cuesta al principio.
  3. Assertions y selectores — Las .should() implícitas y explícitas; la convención data-cy.
  4. Network con cy.intercept() — Mockeá APIs, esperá requests con alias y testeá estados de error.
  5. Custom commands y fixtures — Encapsulá el login y los datos en fixtures JSON para tests limpios.
  6. Component testing + CI — Probá componentes aislados y armá la corrida en el pipeline.

El runner interactivo

Cypress trae un runner visual: con cypress open ves cada comando ejecutarse en vivo y podés viajar en el tiempo a cualquier paso (time-travel). Los tests se organizan con describe() (un grupo) e it() (un caso), igual que en muchos frameworks de JS.

Bash 
npm init -y
npm install --save-dev cypress

# Open the interactive runner (great while writing tests)...
npx cypress open

# ...or run headlessly, e.g. in CI:
npx cypress run
JavaScript 
// cypress/e2e/login.cy.js — Cypress
describe("Login", () => {
  it("greets the user after a valid login", () => {
    cy.visit("https://example.com/login");

    // Commands are queued and retried automatically until they pass
    // or time out — you rarely write an explicit wait.
    cy.get("#username").type("demo");
    cy.get("#password").type("secret");
    cy.get("button[type=submit]").click();

    // .should() re-queries the DOM until the assertion holds.
    cy.get(".welcome").should("have.text", "Welcome, demo");
  });
});

Comandos y la cadena async

El concepto que más cuesta: los comandos cy.* no son promesas y no devuelven un valor directo — se encolan y se encadenan. Si necesitás el valor de un elemento usás .then(), pero conviene evitarlo. Con .as() creás un alias y lo reusás con @nombre.

JavaScript 
// cy.* commands are NOT promises — they enqueue work. You chain, you don't await.
cy.get("#username").type("demo");          // queued
cy.get("button[type=submit]").click();     // runs after the type resolves

// Need the *value*? Use .then() — but reach for it sparingly.
cy.get(".order-total").then(($el) => {
  expect($el.text()).to.eq("250");
});

// Alias a query with .as() and reuse it later with @:
cy.get(".order-items li").as("items");
cy.get("@items").should("have.length", 3);

Assertions y selectores

Las assertions de Cypress son implícitas: .should() reintenta el comando anterior hasta que se cumple. Encadenás más condiciones con .and(), o usás expect() dentro de un callback para casos explícitos. Para selectores estables, la comunidad usa la convención data-cy.

JavaScript 
// Implicit assertions retry the previous command until they pass:
cy.get(".order-status").should("have.text", "PAID");
cy.get(".order-items li").should("have.length", 3).and("contain", "book");

// Explicit assertions with expect() inside a .should() callback:
cy.get(".order-total").should(($el) => {
  expect($el.text().trim()).to.eq("250");
});

// Prefer a dedicated test attribute over brittle css:
//   <button data-cy="pay">Pay</button>
cy.get("[data-cy=pay]").click();

Network con cy.intercept()

Con cy.intercept() interceptás y mockeás las llamadas de red: devolvés datos fijos para tests rápidos y deterministas. Le ponés un alias con .as() y esperás la request con cy.wait('@alias') — nunca un sleep. Cambiando el statusCode probás estados de error (500, 404).

JavaScript 
// Stub the API: deterministic data, no real backend, instant tests.
cy.intercept("GET", "/api/orders/42", {
  statusCode: 200,
  body: { total: 250, status: "PAID", items: ["book"] },
}).as("getOrder");

cy.visit("/orders/42");
cy.wait("@getOrder");                       // wait for the request, not a sleep
cy.get(".order-total").should("have.text", "250");

// Test an error state by stubbing a 500:
cy.intercept("GET", "/api/orders/*", { statusCode: 500 }).as("boom");

Custom commands y fixtures

Repetís un flujo (como el login) en muchos tests: encapsulalo una vez con Cypress.Commands.add() y reusalo en todos. cy.session() cachea la sesión para no re-loguear. Los datos de prueba viven en fixtures JSON y se cargan con cy.fixture().

JavaScript 
// cypress/support/commands.js — encapsulate repetitive flows once.
Cypress.Commands.add("login", (user, pass) => {
  cy.session([user], () => {
    cy.visit("/login");
    cy.get("[data-cy=user]").type(user);
    cy.get("[data-cy=pass]").type(pass);
    cy.get("[data-cy=submit]").click();
  });
});

// cypress/fixtures/order.json -> { "total": 250, "status": "PAID" }
cy.login("demo", "secret");
cy.fixture("order").then((order) => {
  cy.intercept("/api/orders/42", order);
});

Component testing + CI

Además de E2E, Cypress hace component testing: montás un componente aislado con cy.mount() y lo probás sin levantar toda la app. En CI corrés cypress run (headless), con --component o --e2e según el tipo.

JavaScript 
// button.cy.jsx — mount a component in isolation (no full app needed).
import Button from "./Button";

it("calls onClick", () => {
  const onClick = cy.stub().as("onClick");
  cy.mount(<Button onClick={onClick}>Pay</Button>);
  cy.get("button").click();
  cy.get("@onClick").should("have.been.calledOnce");
});

// In CI:  npx cypress run --component   (and --e2e for end-to-end)

Manual vs AI

Manual A mano

Encadenás comandos y assertions con .should(). El auto-retry te quita los sleep, pero vos elegís los selectores y los escenarios.

Con AI Con AI

La AI convierte un caso en lenguaje natural a comandos cy.*, sugiere el .should() correcto para cada verificación y propone data-cy como selectores estables.
